# Обмін замовленнями з BAS через CommerceML 2

Портал реалізує стандартний обмін "1С/BAS CommerceML 2" у напрямку
**сайт → BAS** (тип обміну `sale`, тільки замовлення). BAS сама ініціює
обмін за розкладом (наприклад, кожні 30 хв через "Регламентне завдання
обміну з сайтом"); портал ніколи не звертається до BAS сам.

У BAS вже існують усі клієнти та єдиний склад — портал нікого й нічого не
створює автоматично. Він лише **зіставляє** замовлення з уже існуючими
контрагентами й товарами BAS; якщо зіставити не вдається, замовлення не
надсилається (див. "Захист від помилок" нижче). Магазин/склад із
замовлення в BAS не передається.

## Endpoint

```
https://<домен>/1c_exchange.php
```

Це реальний URL, який потрібно вказати у налаштуваннях публікації обміну
в BAS (майстер очікує саме таку назву файлу). Технічно це rewrite
(`next.config.ts`) на `/api/1c-exchange` — сам handler лежить у
`src/app/api/1c-exchange/route.ts`, а вся бізнес-логіка — у
`src/lib/onecExchange.ts`.

Тестовий URL (локальна розробка): `http://localhost:3001/1c_exchange.php`

## Автентифікація

Кожен запит має містити **HTTP Basic Auth** з технічним логіном/паролем
(окремим від логінів клієнтів порталу — див. змінні середовища нижче).
Неправильні або відсутні креденшали → `401 Unauthorized` з
`WWW-Authenticate: Basic`.

Після `checkauth` BAS отримує сесійну cookie (ім'я + значення в тілі
відповіді, а також через `Set-Cookie`) і має передавати її в усіх
наступних запитах (`init`/`query`/`success`). Без дійсної cookie ці
режими повертають `failure`.

## Режими

### `type=sale&mode=checkauth`

Перевіряє Basic Auth, видає сесію. Відповідь **рівно трьома рядками**:

```
success
cml_exchange_session
1787047946791.2ee3f5eda705acaf5c3711e148803548.618ab919...
```

### `type=sale&mode=init`

```
zip=no
file_limit=10485760
```

### `type=sale&mode=query`

Повертає CommerceML-XML з новими/повторними замовленнями (докладніше —
нижче). Якщо надсилати нічого — тіло відповіді порожнє (стандартний
сигнал "даних більше немає").

### `type=sale&mode=success`

Викликається BAS після успішного завантаження файлу з `query`. Позначає
щойно надіслані замовлення як передані в BAS. Відповідь: `success`.

`mode=file` (зворотна передача статусів із BAS) у цій версії **не
реалізовано** — за поточними вимогами він не потрібен. Якщо BAS
все ж звертається з цим режимом, ендпоінт не впаде — можна додати
обробку пізніше, шар авторизації/сесій вже готовий.

## Формат замовлення

Один запис `<Документ>` = одне замовлення порталу. Кожен товарний рядок —
окремий `<Товар>` всередині `<Товары>`. Валюта — завжди `UAH`. Дата у
форматі `YYYY-MM-DD`, час — `HH:MM:SS` (обидва — за київським часом,
незалежно від таймзони сервера). Суми, ціни, кількість — числа з двома
знаками після коми.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<КоммерческаяИнформация ВерсияСхемы="2.05" ДатаФормирования="2026-08-18T13:12:35">
  <Документ>
    <Ид>cmsyi5hqr00057dlbhewdu276</Ид>
    <Номер>4</Номер>
    <Дата>2026-08-18</Дата>
    <Время>13:10:54</Время>
    <ХозОперация>Заказ товара</ХозОперация>
    <Роль>Продавец</Роль>
    <Валюта>UAH</Валюта>
    <Сумма>24.00</Сумма>
    <Комментарий>Тестове замовлення — один товар</Комментарий>
    <Контрагенты>
      <Контрагент>
        <!-- <Ид> тут = BAS ID клієнта, якщо він відомий (User.basId).
             Якщо його немає — цей тег відсутній, і зіставлення в BAS
             потрібно налаштувати за email+телефоном із <Контакты>. -->
        <Ид>BAS-CTR-00042</Ид>
        <Роль>Покупатель</Роль>
        <Наименование>ТОВ Ромашка</Наименование>
        <ПолноеНаименование>ТОВ Ромашка</ПолноеНаименование>
        <Контакты>
          <Контакт><Тип>Почта</Тип><Значение>client@demo.local</Значение></Контакт>
          <Контакт><Тип>Телефон</Тип><Значение>+380671234567</Значение></Контакт>
        </Контакты>
        <ЗначенияРеквизитов>
          <ЗначениеРеквизита>
            <Наименование>КонтактнаОсоба</Наименование>
            <Значение>Іван Клієнтенко</Значение>
          </ЗначениеРеквизита>
        </ЗначенияРеквизитов>
      </Контрагент>
    </Контрагенты>
    <Значения>
      <ЗначениеРеквизита><Наименование>АдресаДоставки</Наименование><Значение>м. Київ, вул. Хрещатик, 22</Значение></ЗначениеРеквизита>
      <ЗначениеРеквизита><Наименование>СпособОплати</Наименование><Значение>Безготівковий розрахунок</Значение></ЗначениеРеквизита>
      <ЗначениеРеквизита><Наименование>СпособДоставки</Наименование><Значение>Доставка на адресу магазину</Значение></ЗначениеРеквизита>
      <ЗначениеРеквизита><Наименование>СтатусЗамовлення</Наименование><Значение>Нове</Значение></ЗначениеРеквизита>
    </Значения>
    <Товары>
      <Товар>
        <!-- <Ид> = BAS ID товару, якщо відомий (Product.basId), інакше — артикул -->
        <Ид>BAS-PROD-1025</Ид>
        <Артикул>1025</Артикул>
        <Наименование>Вилка Luxel плоска з кільцем (1025)</Наименование>
        <БазоваяЕдиница>шт</БазоваяЕдиница>
        <ЦенаЗаЕдиницу>12.00</ЦенаЗаЕдиницу>
        <Количество>2</Количество>
        <Сумма>24.00</Сумма>
      </Товар>
    </Товары>
  </Документ>
</КоммерческаяИнформация>
```

Стандартні теги CommerceML (`Ид`, `Номер`, `Дата`, `Время`, `Валюта`,
`Сумма`, `Контрагенты`, `Товары`) використані так, як їх зазвичай очікує
типова обробка "Заказ с сайта" в BAS. Спосіб оплати/доставки, статус
замовлення, адреса доставки, промокод і знижка передаються як
`<ЗначенияРеквизитов>`/`<Значения>` — це не строго стандартизовані
теги CommerceML для цих даних, тож у налаштуваннях обробки в BAS їх
потрібно один раз зв'язати з відповідними реквізитами документа "Заказ
покупателя" (за назвою реквізиту, наприклад `СпособОплати`).

## Зіставлення клієнта

1. Якщо в картці клієнта на порталі заповнено **BAS ID**
   (`Адмінка → Клієнти`) — саме він іде в `<Контрагент><Ид>`, і BAS
   шукає контрагента напряму по ньому.
2. Якщо BAS ID не заповнено, але є email і телефон — вони йдуть у
   `<Контакты>`, і зіставлення в BAS потрібно налаштувати "по
   email+телефону" (без автостворення).
3. Якщо немає ні BAS ID, ні телефону — зіставити клієнта неможливо.
   Замовлення **не потрапляє** в жоден XML; воно лишається в стані
   `ERROR` з описом причини і чекає, поки хтось заповнить телефон
   клієнта (`Профіль`) або його BAS ID (`Адмінка → Клієнти`) — після
   цього воно автоматично підхопиться на наступному циклі обміну.

## Зіставлення товару

1. Якщо в товарі заповнено **BAS ID** (`Адмінка → Товари → Змінити`) —
   він іде як `<Товар><Ид>`.
2. Якщо ні — використовується **артикул**: явно заданий у полі
   "Артикул" картки товару, або, якщо він порожній, автоматично
   визначений з назви товару (той самий механізм, що вже
   використовується для пошуку схожих товарів у каталозі).
3. Якщо жодного з двох немає — замовлення з цим товарним рядком **не
   надсилається** (лишається `ERROR` до заповнення артикулу/BAS ID).

Тобто `<Ид>` і `<Артикул>` товару передаються одночасно завжди, коли
`<Ид>` є — саме так, як і питалось: основне зіставлення йде по
узгодженій таблиці `basId`, а артикул лишається запасним/підтверджувальним
ключем.

## Захист від дублів і обробка помилок

- **Дублі.** Кожне замовлення надсилається з постійним `<Ид>` =
  `Order.id` (той самий `id`, що і в базі порталу — незмінний, унікальний).
  Повторне завантаження одного й того ж `<Ид>` в BAS не створює другий
  документ (стандартна поведінка BAS — пошук/оновлення документа за
  зовнішнім кодом). З боку порталу додатковий захист: щойно замовлення
  потрапило у відповідь `query`, воно одразу переводиться в стан
  `SENDING` і зникає з вибірки наступних `query` — тобто навіть повторний
  виклик `query` в межах однієї сесії ніколи не поверне те саме
  замовлення двічі.
- **Стан обміну** (`Order.basStatus`, окремо від статусу самого
  замовлення): `NEW` → `SENDING` (щойно потрапило у відповідь `query`) →
  `SENT_TO_BAS` (після `mode=success`). Якщо `success` так і не прийшов
  (обрив зв'язку, збій обміну) — за 90 хв (три цикли по 30 хв) замовлення
  автоматично повертається в стан `ERROR` і знову потрапляє в наступний
  `query` без втручання людини.
- **Помилка зіставлення** (невідомий клієнт/товар) — замовлення одразу
  позначається `ERROR` з людинозрозумілою причиною в
  `Order.basError` і не потрапляє в XML, поки причину не усунуто.
- Скасовані замовлення (`OrderStatus.CANCELLED`) у BAS взагалі не
  передаються.
- Журнал: кожен виклик `query`/`success` логує кількість
  надісланих/пропущених замовлень і причини пропуску в стандартний лог
  застосунку (у Vercel — вкладка **Logs** проєкту; локально —
  `console.log`/`console.error` у виводі `npm run start`). Окремої
  таблиці журналу немає — для обсягу цього обміну (десятки замовлень на
  цикл) логів застосунку достатньо; SQL-запит нижче показує те саме
  напряму з бази.

Перевірити стан обміну по всіх замовленнях:

```sql
SELECT "orderNumber", "basStatus", "basError", "basSentAt", "basConfirmedAt"
FROM "Order" ORDER BY "orderNumber" DESC LIMIT 20;
```

## Змінні середовища

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `ONE_C_EXCHANGE_LOGIN` | так | Технічний логін BAS для Basic Auth (не пов'язаний з логінами клієнтів). |
| `ONE_C_EXCHANGE_PASSWORD` | так | Технічний пароль. Генерувати окремо, не використовувати пароль адміна. |
| `ONE_C_EXCHANGE_SECRET` | ні | Ключ підпису сесійної cookie. Якщо не задано — використовується `NEXTAUTH_SECRET`. |
| `ONE_C_EXCHANGE_ALLOWED_IPS` | ні | Список IP через кому — якщо задано, запити з інших IP відхиляються (403) ще до перевірки логіна/пароля. |
| `CML_DEFAULT_PAYMENT_METHOD` | ні | Спосіб оплати за замовчуванням для замовлень без власного значення (у чек-ауті це поле поки не збирається). |
| `CML_DEFAULT_DELIVERY_METHOD` | ні | Те саме для способу доставки. |
| `ONE_C_EXCHANGE_BATCH_SIZE` | ні | Максимум замовлень в одній відповіді `query` (за замовчуванням 50). |

Додайте `ONE_C_EXCHANGE_LOGIN`/`ONE_C_EXCHANGE_PASSWORD` у Vercel
(Project Settings → Environment Variables) перед підключенням BAS —
без них ендпоінт завжди повертатиме `401`.

## Інструкція з підключення (сторона BAS)

1. У BAS: **Продажі → Налаштування обміну з сайтом (CommerceML)** →
   вказати адресу `https://<домен>/1c_exchange.php`, тип обміну —
   "Обмін замовленнями" (`sale`), логін/пароль — ті, що в
   `ONE_C_EXCHANGE_LOGIN`/`ONE_C_EXCHANGE_PASSWORD`.
2. У правилах обробки контрагента: пошук за зовнішнім кодом (значення з
   `<Контрагент><Ид>`), якщо відсутній — за email+телефоном із
   `<Контакты>`. **Автостворення контрагента вимкнути** — це прямо
   відповідає вимозі "нових клієнтів не створювати".
2а. Одразу після підключення варто заповнити BAS ID для клієнтів, що
    вже точно є в BAS (`Адмінка → Клієнти`, поле "BAS ID") — це
    найнадійніший ключ і знімає залежність від збігу email/телефону.
3. У правилах обробки товару: пошук за артикулом (`<Артикул>`) або за
   `<Ид>`, якщо він заповнений. Склад для оприбуткування — єдиний,
   фіксований у самій обробці BAS (портал його не передає).
4. Реквізити документа "Заказ покупателя": зв'язати `СпособОплати`,
   `СпособДоставки`, `АдресаДоставки`, `СтатусЗамовлення`, `Промокод`,
   `Знижка` з `<ЗначенияРеквизитов>` XML (див. приклад вище).
5. Запустити регламентне завдання обміну (кожні 30 хв) або виконати
   обмін вручну для першої перевірки.

## curl-команди для ручної перевірки

Підставте свій домен і креденшали. Послідовність нижче повторює те, що
робить BAS: `checkauth` → `init` → `query` → `success`.

```bash
BASE="https://<домен>"
LOGIN="bas_exchange"
PASS="<пароль>"

# 1. checkauth — забираємо ім'я й значення cookie з тексту відповіді
curl -s -u "$LOGIN:$PASS" "$BASE/1c_exchange.php?type=sale&mode=checkauth"
# success
# cml_exchange_session
# <значення>

COOKIE="<значення з попереднього виводу>"

# 2. init
curl -s -u "$LOGIN:$PASS" -b "cml_exchange_session=$COOKIE" \
  "$BASE/1c_exchange.php?type=sale&mode=init"
# zip=no
# file_limit=10485760

# 3. query — тіло відповіді це і є CommerceML-XML із замовленнями
curl -s -u "$LOGIN:$PASS" -b "cml_exchange_session=$COOKIE" \
  "$BASE/1c_exchange.php?type=sale&mode=query"

# 4. success — підтверджуємо отримання
curl -s -u "$LOGIN:$PASS" -b "cml_exchange_session=$COOKIE" \
  "$BASE/1c_exchange.php?type=sale&mode=success"
# success

# 5. Повторний query в тій самій сесії — має повернути ПОРОЖНЄ тіло
#    (ті самі замовлення вже позначені як надіслані/підтверджені)
curl -s -w "\n[%{http_code}, %{size_download} bytes]\n" \
  -u "$LOGIN:$PASS" -b "cml_exchange_session=$COOKIE" \
  "$BASE/1c_exchange.php?type=sale&mode=query"
```

Перевірка помилкових сценаріїв:

```bash
# Неправильний логін/пароль -> 401
curl -s -i -u "wrong:wrong" "$BASE/1c_exchange.php?type=sale&mode=checkauth" | head -1

# query/success без checkauth -> "failure\n..."
curl -s -u "$LOGIN:$PASS" "$BASE/1c_exchange.php?type=sale&mode=query"
```

## Тестові дані

`npx tsx scripts/seed-bas-test-orders.ts` (потребує запущеної локальної
БД, `DATABASE_URL` у `.env`) створює:

- клієнта з BAS ID (зіставлення по `basId`) і замовлення з **одним**
  товарним рядком;
- клієнта без BAS ID, але з телефоном (зіставлення по email+телефону) і
  замовлення з **трьома** товарними рядками (різні товари, різна
  кількість);
- виставляє артикул/BAS ID для кількох реальних товарів каталогу, щоб
  обидва шляхи зіставлення товару (по BAS ID і по артикулу) були в
  одному тестовому наборі.

Ці два замовлення були прогнані через повний цикл
`checkauth → init → query → success → query` локально: XML сформувався
коректно (один `<Документ>` на замовлення, окремий `<Товар>` на кожен
товарний рядок), обидва позначились `SENT_TO_BAS` після `success`, а
повторний `query` повернув порожнє тіло — дублів не було.

Окремо перевірено сценарій помилки: замовлення клієнта без BAS ID і без
телефону виключається з відповіді `query`, лишається в стані `ERROR` з
описом причини та автоматично підхоплюється, щойно телефон/BAS ID
заповнять.
